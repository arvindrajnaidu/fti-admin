Decisions 10

Choices made where the spec was silent or ambiguous, and resolved before build.

Decision

Phase 1 = Parts 1+2+3 + Part 4 write-only

spec §3 + §4

Confirmation page writes to recipients/{phoneE164} so the profile collection accumulates real data from day one. The order-write API does not read from the profile yet — no silent pre-fill of incoming orders. Auto-fill is phase 2.

Decision

Order doc schema stays as-is

spec §4 schema

Existing recipient.* fields (doorNo, addressLine, landmark, location.formattedAddress) are untouched. The 7-field structured address (doorFlat, street, landmark, area, city, state, pincode) only lives in two new places:

Stored in
  • recipientContact.confirmedAddress on the order doc
  • recipients/{phoneE164}.confirmedAddress profile
Decision

Time-change email is sent by admin, not foodtoindia

spec §2 on-submit step 3

Resend integration + templates already live in admin. Adding a second Resend client to foodtoindia is unnecessary surface area. Flow:

  • /api/confirm-order in foodtoindia sets recipientContact.pendingSenderNotification = true when the recipient changed the time.
  • Admin (existing Resend infra) picks the flag up and sends. Pickup mechanism is TBD in plan mode — likely lightweight polling.
Decision

Token: crypto.randomUUID(), no expiration

spec §1 on-click step 1

Order lifecycle handles invalidation — once delivered or cancelled, the page renders "already processed" regardless of token state. No background expiry job needed.

Decision

"No WhatsApp" treatment only fires for non-IN recipients

spec §1 (silent) · build feedback 2026-05-18

Sender opt-in flag is a hint, not a gate — button always stays clickable. Initial gating bug (caught during build): recipientPhoneIsWhatsApp === false flipped the button to gray with "marked as no WhatsApp — call instead". But the cart's WA checkbox is a plain boolean with no "user didn't engage" state, and it defaults unchecked for IN recipients — which flagged almost every IN order incorrectly.

Fixed gating in senderMarkedNoWhatsApp(order): treat the boolean as a real signal only when the country is non-IN. For IN we always show the default green WA button — WhatsApp penetration is ~95% and ops falls back to a phone call if WhatsApp bounces on the rare landline-only exception.

Long-term fix is a tri-state field (true | false | null) so we can distinguish "user said no" from "user didn't engage" — but that's a schema + cart-UI change. Country-gating captures the value at zero data-model cost.

Decision

Re-sending WhatsApp re-uses the same token; only timestamp updates

spec §1 (silent)

Avoids invalidating a link the recipient may still be looking at from the first message. Clean idempotency: one token per recipientContact, lifecycle-bound.

Decision

No "no-response after 4h" cron in phase 1

spec §3 status badges

Spec lists a "No response" (red) status implying background detection. Keeping it manual: dispatch row shows the whatsappSentAt timestamp and ops judges. Re-visit when Tool 3 (dispatch monitoring cron) ships — that's the natural home.

Decision

English-only WhatsApp message in phase 1

spec §1 templates

Six template variants all English. Hindi / Punjabi deferred until founder provides translations or volume justifies localization tooling.

Decision

Three-tier deliver-at storage on order doc

spec §3 deliver-at

Spec says ops's manual time entry "overrides sender's" but doesn't specify the storage shape. Chose three separate fields with a clear precedence so the original sender / recipient signals are preserved (useful for analytics + dispute resolution):

  • scheduling.scheduledFor — sender's checkout choice (unchanged)
  • recipientContact.confirmedTimeSlot — recipient's choice via confirmation page
  • recipientContact.opsConfirmedTimeSlot — ops manual entry from WhatsApp chat

The effectiveDeliverAt(order) helper picks the winner: ops > recipient > sender.

Decision

Firestore composite index for collectionGroup('orders') created proactively

spec §2 + plan phase C

db.collectionGroup('orders').where('__name__', '==', orderId) requires a collection-group-scoped index on the __name__ field. Firestore's default single-field auto-indexes do not cover collection-group queries. First call to /api/confirm-order-lookup would fail at runtime with a "needs index" error pointing to a console link.

We add the index to firestore.indexes.json in foodtoindia/ and deploy with firebase deploy --only firestore:indexes as part of Phase C — before the first end-to-end test of the confirmation page.

Tradeoffs 2

Choices where multiple valid options existed and the path picked needs to be auditable later.

Tradeoff

Public order lookup uses collectionGroup('orders')

spec §2 security

Orders live at users/{uid}/orders/{orderId} but the confirmation page URL only carries the order ID, not the uid.

Options considered
  • Chosen: db.collectionGroup('orders') filtered by orderId + token. Same pattern as scripts/_check-order-recipient.js. No schema change. Single Firestore read.
  • Denormalize uid into URL (/confirm/[uid]/[orderId]) — leaks the uid in WhatsApp-shared links.
  • Mirror to flat /confirmations/{orderId} doc — doubles writes, adds a sync path to maintain.

At 47 orders/week the scan is cheap. Re-evaluate at 500+ orders/week.

Tradeoff

Confirmation page scheduling = checkout scheduling, not spec's 1-hour windows

spec §2 delivery time

Spec proposes 1-hour windows on the confirmation page. Customer checkout uses 30-minute slots. Choosing alignment.

Options considered
  • Chosen: 30-minute slots, "ASAP" hidden outside 8 AM – 9:30 PM IST ops hours, 2-hour buffer. Re-uses lib/scheduling.js (getDateOptions, getSlotsForAnchor, isWithinOpsHours, formatSlotLabel).
  • Follow spec verbatim with 1-hour windows — creates a separate slot model + validator + UI grid for what is effectively the same dispatch decision.

Rationale: two flows that lead to the same dispatch decision shouldn't disagree on the time grid. Different grids would create UX surprises and validation edge cases.

Deviations 3

Places where implementation intentionally departs from spec text.

Deviation

recipient.recipientName → recipient.name

spec §1 variable sources

Spec §1 references recipient.recipientName; the actual field on the order doc is recipient.name. Following the doc. Pure naming correction — no behavior change.

Deviation

Dispatch queue is a flat table — no Overdue/ASAP/Scheduled sections (yet)

spec §3 dispatch enhancements

Spec §3 + the strategy doc both reference an "existing Overdue / ASAP / Scheduled sections" structure in the dispatch queue. The current admin/pages/orders.js is one flat table — those sections don't exist today. Phase 1 ships the per-order capabilities (WA button, status pill, set-deliver-at modal, ops address editor) without rearranging the layout into sections. The sort behavior (by effective deliver-at within sections) is also deferred until sections actually exist.

Deviation

Deliver-at column on table deferred; modal-only entry point

plan phase D

Plan called for a "Deliver at" column on the dispatch table that ops could click to edit. Ship 1 wires editing through the order detail modal instead (new "Set deliver time" + "Edit address" buttons next to existing Cancel/Issue Store Credit). Reasoning: the existing modal is already the per-order action surface; adding a new column required a larger table-layout change for minimal additional value at 47 orders/week. Soon-cue background tinting (within 30 min of delivery) also deferred for the same reason.

Phase 2 candidate: add the column when the volume of pending orders justifies surfacing the timestamp inline.

Open questions 1

Things that surface during implementation and need your confirmation or revision.

Open

API + page tests deferred to phase 2

phase 1 verification

Phase 1 ships with 47 passing unit tests across tests/lib/whatsappTemplates.test.js and tests/lib/recipientProfile.test.js — covering both pure-function libraries end-to-end.

Not covered: the new API routes (confirm-order-lookup, confirm-order, log-sent, set-deliver-at, set-address, send-time-change-notification) and the React confirmation page. API tests need Firestore collectionGroup + transaction + batch mocks; the page needs Playwright E2E. The existing tests/pages/api/orders.test.js only does minimal validation testing — building full mocks here is the right call later, not now.

Recommendation: cover with Playwright E2E once the feature is manually verified against dev Firestore.

Retrospective — what wasn't well thought through the first time

Honest accounting of the gaps the user had to surface during build, so the next feature avoids the same shape of misses. Most of these were not spec ambiguities — they were workflow blind spots: the spec was followed but the actual ops experience wasn't traced end-to-end before code shipped.

Process miss

Confirmation feedback loop was missing

user spotted 2026-05-18

Built the recipient-side flow (page, API, writes, profile upsert, time-change email) but didn't think through how ops discovers a confirmation has landed. The recipient hit a "Thank you" page; ops had no visual signal on the dispatch queue. The recipientContact.status === 'confirmed' field was written but no card UI consumed it.

Fix: ✓ Confirmed pill on the dispatch card next to the recipient name. Auto-refresh + Slack alert flagged for follow-up.

Lesson: after building the "primary actor" flow (recipient), trace each affected actor's feedback path explicitly. Ask "how does X see this happened?" for every state transition.

Process miss

Mobile card design needed five iterations

user feedback 2026-05-18

Initial cards were generic React-y rows. Visual hierarchy was flat, no anchor for scanning, ambiguous labels (no "Sender" / "Recipient" distinction). Took the user five rounds of feedback to land on a layout they'd accept: bike-vs-clock icon, time as primary, "Sender: X · May 17" footer.

Lessons:

  • "Visual hierarchy" isn't an output you arrive at — it's a design input. Sketch the card in ASCII or HTML before writing the component, in 3-4 distinct variants, and have the user pick. Saves rounds.
  • Avoid color decoration ("AI slop" — user's word) for purely decorative purposes. Color carries meaning or doesn't appear. The left rail I added was decoration; the inline red lateness is meaning.
  • Reference real ops tools (DoorDash dispatcher, Apple support, Airbnb host dashboard) before the first draft, not after the user mentions them.
Process miss

Stale modal state — twice

user spotted 2026-05-18

After ops saved a delivery time, the modal kept showing the old ASAP state. Same bug for address: "Current address on file" showed the original sender address even after ops's update.

Root cause was the same in both: selectedOrder was a snapshot, not a derived view. Optimistic updates patched one field but reads pulled from a different field (scheduling.scheduledFor vs recipientContact.opsConfirmedTimeSlot). Required getEffectiveScheduling() / formatCurrentAddress() helpers plus a sync effect to fix.

Lesson: when a feature has three sources for one logical value (sender / recipient / ops), build the precedence helper first, write it once, use it everywhere. Don't read raw fields in components — always go through the helper. The "stale modal" was actually the symptom; the underlying issue was reading from the wrong field.

Process miss

Firestore lookup query was silently broken

user spotted 2026-05-18 via "link invalid"

The public confirm page used collectionGroup('orders').where(FieldPath.documentId(), '==', orderId) — but Firestore requires the value to be a full document path (4 segments), not a bare ID. The query threw at runtime; the API caught it and returned 500; the page mapped any non-2xx to "link invalid or expired."

Three failures stacked: (a) wrong query, (b) catch-all error message hiding the cause, (c) no integration test that would have caught it before user-facing testing.

Lessons:

  • Test the Firestore query path end-to-end with a real doc ID in a script before the UI lands on it. The scripts/_check-confirm-token.js diagnostic should have been written during Phase C, not after a failure.
  • Don't collapse different error states ("link bad" vs "server error") into one user-facing message. Even an internal "Server error — try again" would have prompted the user to check logs instead of doubting the link.
  • When designing public-page lookup by parent-scoped resource, use a top-level shadow doc (confirm-lookups/{orderId}) — the indirection layer avoids collection-group quirks and is the right privacy model.
Process miss

Defaults didn't match ops's actual context

user feedback 2026-05-18

Three defaults I picked wrong:

  • "No WhatsApp" treatment for IN recipients — flagged every IN order as "call instead" because the cart defaults the checkbox unchecked. India has ~95% WhatsApp penetration. Fix: country-gate the check to non-IN only.
  • 3-4 day scheduling range for ops — copied the customer-flow range without thinking about ops's actual use case (WhatsApp conversations sometimes commit to "next Friday"). Fix: getDateOptions takes a maxOffset param; ops passes 6 for 7-day range.
  • Door / Flat marked required with asterisk — validation already accepted Street alone, so the asterisk was a lie. Removed.

Lesson: default values are decisions, not placeholders. For every default I copy from another flow, ask "is the user-context the same?" The customer is choosing a delivery time for themselves; ops is committing to a verbal promise from a WhatsApp chat. Different contexts, different defaults.

Process miss

Set ASAP needed a confirmation prompt

user spotted 2026-05-18

"Set ASAP" was a one-tap action that overwrote any scheduled time without warning. User flagged it: ops could lose a carefully-negotiated WhatsApp time with a misplaced tap.

Lesson: destructive actions need confirmation even in internal tools — especially when the action is reachable from the same modal as the non-destructive primary action. The "Save time" and "Set ASAP" buttons sit next to each other; one overwrites the other's intended state. Confirmation on the destructive one is cheap insurance.

Process miss

Modal navigation broke flow

user spotted 2026-05-18

First version: tapping a dispatch card navigated to /orders?openOrder=…. The URL changed; ops lost their place in the dispatch list. User wanted an in-place modal on the dispatch page.

Lesson: when adding click-through to a list view, default to in-place modal (no URL change) unless there's a specific reason to navigate. Navigation is for "show me a different view of this thing"; modal is for "let me act on this thing without losing my place."

Pattern across all of these

I built to the spec but didn't walk the ops journey end-to-end before declaring Phase 1 done. Each iteration was the user noticing a step in their workflow that hadn't been thought through. Better practice next time:

  • After spec → before code: write a narrative of the user (ops, recipient, sender) walking through the feature on mobile and desktop. Identify every screen, every state, every feedback loop.
  • For each state change on the server, list every actor affected and how each finds out. Don't ship until each path is explicit.
  • Build precedence/derivation helpers before components consume the data. Components read through the helper, never raw.
  • Write integration scripts during build, not after a failure. Treat the "happy path script" as part of the deliverable, not as debugging tooling.
  • For internal tools, copy patterns from reference ops apps (DoorDash, Stripe Dashboard, Linear) at design-sketch time, not after rounds of feedback.
