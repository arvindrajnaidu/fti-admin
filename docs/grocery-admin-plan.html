Current state — what's actually broken today. Verified against the code:
  • Grocery orders are written to a separate subcollection: users/{uid}/grocery_orders/{paymentIntent.id} (see website/lib/grocery-order.js:320-324). Doc IS stamped with orderType: "grocery", but lives in a different collection from food.

Fixing the invisibility is the floor for shipping grocery to real customers.

1.Why split Ops, not Reports

The consumer plan separated experiences because users are intent-driven and don't browse across modes. The admin counterpart is the same shape, but the cut runs through a different layer: Ops, not Reports.

AreaSplit by mode?Why
Ops (Orders, Dispatch, Inbox) Yes Different SLAs (food: hot, <2h; grocery: scheduled, multi-hour). Different fulfilment paths (food: direct-to-restaurant calls; grocery: Instamart/Blinkit upstream). Different exception handling. A dispatcher staring at one queue gets faster decisions than one filtering between two.
Reports (Analytics, Customers, Attribution, Referrals, Upsell) Not yet A customer is a customer regardless of which product they buy. We want unified LTV, attribution, referral attribution. Grocery volume is too thin to support its own cohort views. Revisit when grocery clears ~50 orders/week.
Marketing (Email Campaigns, Templates, Promo Codes) Not yet Same reason — and most outreach is account-level, not mode-level. Per-mode promo codes already work via the existing scope field; no nav split needed for that.
Store Credits, Abandoned Carts Decide later Store credits are account-scoped (a credit applies anywhere) — leave shared. Abandoned-cart emails are mode-coupled (the email links into /food or /grocery) but the queue + sending tools are shared. Cross that bridge when grocery abandoned-cart tracking lands.
Decisions locked (the contract for this PR):
  • Nav structure: Ops becomes two sub-groups — Ops · Food and Ops · Grocery. Reports, Marketing, and the remaining shared items stay as today.
  • Routes: grocery surfaces live under /grocery/*. Existing food paths (/, /orders, /inbox) keep their URLs — no rename in this PR. (Whether food eventually moves to /food/* mirrors the consumer-side URL migration and is its own decision.)
  • Scope (NOW): two grocery pages — /grocery/orders and /grocery/dispatch. Nothing else.
  • Dispatch: separate page per mode (§5). Trade-offs called out; the call is "separate, with a clear pivot point if/when it bites."
  • Backend: a new sibling endpoint /api/grocery-orders reads the grocery_orders subcollection. The existing /api/orders is untouched (still scans orders only). No mixing in a single route — they're different doc shapes (different currency, different ID format, different field set), and a thin shared buildOrdersResponse(collection, options) helper is cheaper than the per-row mode branching a merged route would need. See §6.
  • Currency: grocery is USD (Stripe charge currency), food is INR. Admin renders each in its native currency — no conversion in this PR. Ops-facing INR equivalent for grocery (for buying from Instamart) is a NEXT item.
  • Deferred: grocery-specific reports, abandoned-cart emails, store credits scoping, attribution, referrals. Listed in §7.

5./grocery/dispatch — and the merge-vs-split call

The open question, stated plainly. Two options for dispatch:
  1. Separate — / stays food-only dispatch, /grocery/dispatch is its own page. Two queues, one per mode.
  2. Merged — one dispatch page lists everything in flight, with a mode column / filter chip. One queue.
Below is the trade-off. The recommendation is separate.
Separate (recommended)Merged
Dispatcher mental load Lower. One mode, one set of actions, one set of states. Matches how the work actually happens — different fulfilment paths, different SLAs. Higher. Every row needs a mode glance before any action. Food and grocery have different action vocabularies (food: "called restaurant"; grocery: "Instamart accepted").
Cross-mode awareness Lost — but it wasn't a problem we were solving. Same customer's two orders rarely need joint action. Gained — useful only if one dispatcher actually handles both modes simultaneously. Today that's not how the team operates.
Action surfaces Each page only renders actions valid for its mode. Cleaner row UI; no conditional rendering per row. Every action needs a mode-guard. Conditional UI per row. Easy to ship a bug where a food action shows on a grocery row.
Volume asymmetry Grocery page may sit nearly empty for weeks. Fine — it's the right home when work shows up. Food rows dominate the view; grocery rows scroll off easily. Worse for the low-volume mode, which is the one most likely to be missed.
If we change our mind Easy to merge later — just compose the two queries. Harder to split later — UI assumptions ("one queue") leak into components.
Pivot point. If we hit a state where one dispatcher routinely toggles between / and /grocery/dispatch ten times in an hour, that's the signal to revisit. Until then, separate.

6.Data & API plumbing

The food and grocery order docs live in different subcollections, in different currencies, with different doc-ID shapes. A single filtered route hides those differences but pays for it with per-row mode branching everywhere downstream. Cleaner: a sibling endpoint with its own cache, and a small shared helper for the parts that are the same (auth, fraud-user skip, per-user fetch batching).

The endpoint

Add pages/api/grocery-orders.js as a sibling of pages/api/orders.js. Same structure, different collection name and a different cache key:

// pages/api/grocery-orders.js — sketch
const ordersSnapshot = await db
  .collection('users')
  .doc(userId)
  .collection('grocery_orders')   // ← not 'orders'
  .get();
// ... same per-doc shape massage as /api/orders, then:
//   - flatten, sort by createdAt desc
//   - cache under global.groceryOrdersCache (separate key)
//   - same 5 min TTL
//   - same fraud-user skip via isValidUser(senderEmail)

This keeps the food code path 100% untouched. Grocery pages call /api/grocery-orders; nothing about the existing food fetches changes.

Cache invalidation — don't break the existing call sites

Implementation hazard surfaced in code review. Today global.ordersCache = null is invalidated from six separate API routes (cancel-order, store-credits, four whatsapp/* routes). If we naively rename the global to a map (global.ordersCache[type]), every one of those six call sites breaks silently — admin will show stale rows on edit. Two acceptable options:
  1. (Recommended) Centralize the food cache as-is. Keep global.ordersCache exactly as today; the six invalidators don't change. Grocery introduces a new global, global.groceryOrdersCache, scoped only to /api/grocery-orders. No back-compat surface; no rename pressure on food code.
  2. Introduce a tiny lib/ordersCache.js with invalidate('food' | 'grocery' | 'all') and refactor all six call sites to use it. Cleaner long-term, but a much bigger blast radius for what should be additive work. Defer to a follow-up unless we're touching those files anyway.
Going with option 1. Two globals, zero changes to existing invalidators. (Grocery has no admin mutation surfaces yet, so its invalidation list starts empty — easy to grow.)

The two new pages

pages/grocery/orders.js and pages/grocery/dispatch.js. Both fetch /api/grocery-orders. Reuse AdminShell, PageHeader, TableShell verbatim. Column lists and the currency formatter are the only material differences. Dispatch filters client-side to status === 'created' (server returns the full list; the open-queue cut is presentation).

Order detail page — what happens when a row is clicked

Order detail — minimal page in NOW (locked v0.4). Per code-review consensus: non-clickable rows in a list pattern read as broken, and grocery ops will need at least recipient, line items, total, Stripe PI link, notes, and store metadata to actually act on an order. So /grocery/orders/[id] ships in NOW as a minimal page — not a port of the full food detail surface.

In scope (NOW):

  • Order header — ID (full pi_* with copy + Stripe Dashboard deep link), source badge, status, placed-at, total in USD.
  • Sender block — name, email.
  • Recipient block — name, phone, address.
  • Store metadata — provider, store ID, store name, area/city (whatever's on the doc once consumer-side widening lands; degrades to ID-only otherwise).
  • Line items table — name, qty, unit price, line total.
  • Totals breakdown — subtotal, delivery fee, tax, total.
  • Internal notes — reuse the existing InternalNotes component (mode-agnostic, just needs an order ref).

Out of scope (NEXT): delivery-confirm modal, WA action panel, Stripe Radar risk panel, provider-state timeline. These all assume backing fields or workflows that don't exist on the grocery side yet.
