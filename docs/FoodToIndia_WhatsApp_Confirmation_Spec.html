WhatsApp Recipient Confirmation

Replace the founder's manual recipient-confirmation phone calls with a one-click WhatsApp deep-link from the admin dispatch queue, plus a public confirmation page where recipients verify address and delivery time. State lives on the order doc; addresses accumulate in a global recipients/{phoneE164} profile.

Status Approved for build Owner Athahar Repos admin · foodtoindia Phase 1 scope Parts 1–3 + Part 4 write-only
⚖️
This spec is the goal. Implementation choices that diverge from it — schema mappings, lookup strategy, where the time-change email is sent — are tracked separately in implementation-notes.html. Read both side-by-side when reviewing the build.

00Context & goal

Our ops person currently calls or WhatsApps recipients manually to confirm delivery address and timing before placing orders on Swiggy or Zomato. This is untracked — no record of when contact was attempted, what was confirmed, or what time the recipient requested. If the ops person forgets a detail from a WhatsApp conversation, orders get delayed or fail.

Three deliverables

  • A "Send WhatsApp" button on each order in the dispatch queue that opens WhatsApp with a smart pre-formatted message.
  • A public recipient confirmation page (no auth) where recipients confirm their address and pick a delivery time via the link in the WhatsApp message.
  • Dispatch queue enhancements — "Deliver at" field, ops address editing, and "Ready to dispatch" status logic for repeat recipients.

01End-to-end flow

How a single order moves through the system, from cart submission to final dispatch. Each numbered step is a state change on the order doc; dotted paths are conditional.

02Part 1 · WhatsApp button on dispatch queue

Location

The dispatch queue page (the existing Overdue / ASAP / Scheduled sections in admin/pages/orders.js). Add a WhatsApp icon button on each order row, next to the recipient info.

On click

  1. Generate a 32-char token and store it as recipientContact.confirmToken on the order doc.
  2. Build the confirmation URL: https://foodtoindia.com/confirm/[orderId]?token=[confirmToken].
  3. Pick the message template based on three conditions (see message logic below).
  4. Open the WhatsApp deep link: https://wa.me/[phone]?text=[encoded] — phone from recipient.recipientPhoneE164, strip the leading +.
  5. Log the contact attempt on the order doc (see schema: recipientContact object, status 'pending').
  6. Show "WA sent" indicator on the dispatch row with the timestamp.

Message logic

The message content depends on three conditions:

Condition Check Source
A. Full address on order Both door/flat number and street/address line are set on the recipient — not just area/locality. recipient.doorNo & recipient.addressLine
B. Sender chose delivery time Scheduled delivery time is set on the order. scheduling.scheduledFor
C. Confirmed profile on file Recipient has a previously-confirmed address in recipients/{phoneE164}. Part 4 lookup

03Part 2 · Recipient confirmation page

Route

/confirm/[orderId] in the foodtoindia/ app. Public — no authentication required.

Security

URL carries ?token=[confirmToken]. The page calls /api/confirm-order which validates both order ID and token before any read or write. The public page never touches Firestore directly.

StatePage renders
Invalid token"This link is invalid or has expired."
Already processed"This order has already been processed." (delivered / cancelled)
Already confirmed"You've already confirmed this delivery. If you need to make changes, please reply to our WhatsApp message." No re-submit allowed.
PendingFull form (default state).

Page content

Address section

  • Area / Locality — pre-filled from order; read-only if it determines restaurant availability.
  • Door / Flat No. — text input.
  • Street / Address Line — text input.
  • Landmark — text input. Helper: "Helps the delivery driver find you."

Delivery time section

  • Sender picked a time: show "Your order is scheduled around [Time] IST" with two buttons — "This works" / "I need a different time."
  • No time set: show the slot picker directly.
  • Slot grid: 30-min slots in IST. Only slots ≥ 2 h from now. "ASAP" option included during ops hours only.

On submit

/api/confirm-order validates token, then atomically:

  1. Updates the order doc — recipientContact.status = 'confirmed', confirmedAt, confirmedAddress, confirmedTimeSlot. If time changed, timeChanged = true.
  2. Upserts recipient profile at recipients/{phoneE164} — sets confirmedAddress, addressSource = 'recipient_confirmed', addressUpdatedAt, name, lastOrderId.
  3. If time changed, flag pendingSenderNotification: true so admin can email the sender via the existing Resend integration.
  4. Renders confirmation — "Thank you! Your delivery details have been confirmed. [Sender First Name] is sending you something special."

Sender notification email (Resend, from admin)

Subject: Delivery time updated for [Recipient Name]

Body: [Recipient Name] has updated the delivery time to [New Time] IST. We'll deliver at the updated time.

Mobile-friendly. Almost every open is from a phone via WhatsApp. Large tap targets, no unnecessary scrolling, single-column layout.

04Part 3 · Dispatch queue enhancements

"Deliver at" field

Editable date/time field on each dispatch-queue row.

SourceWins when
Sender at checkoutDefault, if nothing else has happened.
Recipient via confirmation pageOverrides sender's time. Highest signal of recipient intent.
Ops manual editOverrides both — ops captured a verbal commitment over WhatsApp.

Sort & visual cues

  • Within each section (Overdue · ASAP · Scheduled), sort by "Deliver at" ascending. Untimed orders sort last.
  • Within 30 min of delivery window → soon yellow background.
  • Past delivery window → overdue red styling (existing pattern).

Ops address editing

  • Click to open address form on a row. Edit door/flat, street, landmark, area, city.
  • On save, write to both: the order's delivery address and the global profile recipients/{phoneE164} with addressSource = 'ops_updated'.
  • Show a transient "Address updated" toast.

Status badges on each row

Ready green
Confirmed address + sender time. Dispatch without contacting.
Confirmed green
Recipient confirmed via the page. Both address & time set.
WA sent yellow
WhatsApp sent, awaiting reply. Timestamp visible.
Pending grey
No contact attempt yet.
No response red
WhatsApp sent > 4 h ago, no recipient action. Phase 1: ops judges manually from timestamp.

05Part 4 · Recipient profile & repeat customers

Profile collection

New Firestore collection recipients/{phoneE164}, keyed by the recipient's phone in E.164 format (e.g. +919003712800).

// recipients/{phoneE164} { name: string, confirmedAddress: { · doorFlat: string, · street: string, · landmark: string, · area: string, · city: string, · state: string, · pincode: string }, addressSource: 'recipient_confirmed' | 'ops_updated', addressUpdatedAt: timestamp, lastOrderId: string }

When to update

  • Recipient confirms via the public page → addressSource = 'recipient_confirmed'.
  • Ops edits address in dispatch queue → addressSource = 'ops_updated'.
  • Last write wins, regardless of source.

When a new order arrives

Look up the recipient phone (E.164) in recipients/:

Profile address exists

  • Pre-fill full address on new order from profile.
  • Show "Confirmed address on file" badge in dispatch row.
  • If sender also picked a time → Ready.
  • If no time → WhatsApp asks only about timing.

No profile

  • Use whatever address the sender provided.
  • Follow standard WhatsApp template flow (variants 3–6).
⚠️
Edge case: if the sender entered a different area/city than what's on the profile, do not auto-fill from the profile. Recipient may have moved, or the sender is sending to a different location. Treat as a new address.

07What this does NOT include (intentionally)

×
WhatsApp Business API / Twilio integration. We're using manual WhatsApp via deep links. Graduate to the API when volume exceeds 100 orders/week.
×
Automated WhatsApp sending. Ops clicks the button manually. No cron-based auto-sending.
×
AI/LLM for parsing WhatsApp replies. Ops reads replies and updates the dashboard manually. The confirmation page handles structured data capture.
×
Reminder system for ops. "Deliver at" sorting + yellow/red visual indicators serve as the reminder. No separate notification system yet.

08Implementation deltas

For the running log of design choices made during implementation that depart from or interpret this spec, see implementation-notes.html. Key deltas already known:

  • Order doc shape: the existing recipient.* fields stay unchanged. The 7-field structured address only appears in recipientContact.confirmedAddress and recipients/{phoneE164}.confirmedAddress.
  • Profile lookup: Phase 1 writes profiles when the recipient confirms. The auto-fill on incoming orders (Part 4 "when a new order arrives") is deferred to phase 2.
  • Order lookup from public page: uses collectionGroup('orders') since the URL only carries the order ID, not the uid.
  • Time-change email: sent from admin (existing Resend infra). foodtoindia writes a flag.
  • Field naming: spec says recipient.recipientName; doc field is recipient.name. Implementation uses the doc.
